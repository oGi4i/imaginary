# Native memory CI

The `Native memory CI` workflow runs on pushes to `mitigate-native-memory` and by manual dispatch. GitHub requires the workflow file on the default branch before manual dispatch is available. A branch push can run it before then.

The GitHub-hosted Ubuntu 22.04 runner installs build dependencies, verifies the SHA-256 of the [libvips 8.10.0 release archive](https://github.com/libvips/libvips/releases/tag/v8.10.0), and builds libvips from source. It installs Go 1.20.14, downloads Go modules including bimg v1.1.4 with `go.sum` verification, and runs `go mod verify`. It checks formatting of Go files changed since v1.2.4, then runs all package tests, the race detector, `go vet`, and a binary build. The build preincludes C++ `type_traits` to avoid a GLib header being included with C linkage by the old libvips headers. The libvips build disables SVG: libvips 8.10.0 expects a librsvg header absent on this runner. SVG decoding is not tested. The build enables Poppler for PDF loading and checks that the PDF loader is present; this does not prove that PDF parsing is bounded or safe. Module updates are disabled. The workflow does not publish the binary or an image and needs no secrets. After module verification, the body-limit boundary test, focused source regressions, full tests, race tests, vet, and compilation run as separate checks, even if an earlier check fails. Cancellation or failed module verification skips these checks. The focused check selects `TestRasterSourcePNGHeaderFields`, `TestRasterSourceReadFailuresBypassPlaceholder` (including empty inputs), `TestRasterSourceOversizeReadBypassesPlaceholder`, `TestRasterSourceRejectsWatermarkImageBeforeFetch`, and `TestRasterSourceInvalidParamsBypassPlaceholder` before the full suite. The body-limit check retains the exact `^TestBodyLimitRawPOSTBoundaries$` target. Both focused checks have a 60-second external deadline and a 50-second Go test timeout; full and race tests have five-minute external deadlines and four-minute Go test timeouts. Vet and compilation each have 120 seconds. GNU `timeout --signal=KILL` sends SIGKILL at each external deadline to its default process group, without `--foreground` or a TERM grace period. This covers native code that ignores Go's timeout and children that ignore TERM while they remain in that group. Descendants that escape into another process group or session are not covered; this is not a guarantee that all descendants terminate.

The user authorized one exact-hash bimg v1.1.4 WebP correction. After original
module verification, a shared source-owned helper stages the module and replaces
only existing file `resizer.go`. Because the original v1.1.4 module ZIP lacks
`go.mod`, the staged local replacement also needs one exact synthetic module
declaration. Its source identity records original and patched sizes and SHA-256
values. A temporary module file selects that exact staged module for all
tests, race checks, vet and compilation; tracked module files remain unchanged.
The runtime-image preparer must use the same helper and identity, as must any
future instrumented upstream-source baseline. A source-side patch is not proof
that either patched comparison image was built. Small-target WebP, portrait,
thin-axis and preload-boundary regressions remain native CI requirements.

This is a test environment, not a qualified production image. The existing Dockerfile uses Debian Buster; the Ubuntu runner uses a different glibc and different native dependencies. Results do not establish production ABI compatibility or memory behavior. The runner image, OS packages, and other build inputs are not fully pinned; the archive checksum and action commit pins do not make the build reproducible. The workflow does not alter the existing Dockerfile.

The release archive uses SHA-256 `1299d3a98213ae477f0180817ec79afd36803a5b8434f48068e75a721d23b6f9`. libvips configuration options can be checked in the release archive's `configure --help`; upstream [build notes](https://github.com/libvips/libvips/blob/v8.10.0/README.md) describe its dependencies. GitHub documents [workflow triggers](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) and [manual dispatch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
